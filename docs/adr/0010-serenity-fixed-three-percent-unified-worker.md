# 0010 — Serenity 固定 3% 与统一 Worker 故障隔离

- **Status:** Accepted
- **Date:** 2026-07-24
- **Supersedes:** ADR 0008 中 Serenity 的 0%-8% 因果晋升幅度；ADR 0004 的独立容器拓扑

## Context

Serenity 的独立容器在合同内核切换时被删除，但采集没有真正迁入统一 worker，生产计划因此始终写入零权重。用户希望 Serenity 参与推荐，同时不让公告数据源的缺失或故障偏袒部分股票，并将最大影响进一步收窄到固定 3%。

## Considered Options

1. 恢复独立 Serenity 容器并继续 0%-8% 自动晋升。
2. 在请求或计划线程内同步抓取公告。
3. 在统一 `gp-worker` 中隔离运行采集，以目标批次原子门控固定 0%/3% 贡献。

## Decision

选择方案 3。Adaptive 基础分数先稳定排序并产生 Top-30 目标。Serenity 对该精确目标和交易日期异步生成不可变批次。只有候选覆盖完整、来源成功、解析完成、未过期且目标摘要完全匹配的批次才整体启用固定 `0.03` 权重；其他状态统一对全部候选使用 `0.00`。

完整批次中的 alpha 被限制在 `[-1, 1]`，候选最终输入分数为 `clamp(base_score + 0.03 * alpha, 0, 1)`。没有相关证据的完整候选 alpha 为 0。Serenity 不拥有候选集合、基础分、阈值、行动或最终选择权。

采集在 `gp-worker` 的独立执行单元中运行，具有独立 lease、超时、退避、异常边界和健康状态。推荐生成只读取已原子提交的兼容批次，绝不等待网络。合格批次的稳定身份进入 `PlanLookupKey`；所有不可用状态映射为同一个零权重哨兵。

## Rationale

整批门控消除了按股票数据可得性不同造成的不对称影响。固定 3% 给公告证据有限且可审计的参与空间，同时保持 Adaptive Decision Engine 的决定权。统一部署减少常驻容器，但隔离执行单元避免 Serenity 的慢请求或崩溃拖垮基础推荐循环。

## Consequences

- Serenity 数据源失败只表现为权重 0 和可观测降级，基础推荐继续。
- 新完整批次可产生新的不可变计划；反复失败不会造成计划版本抖动。
- 同一容器内的独立子进程仍共享容器级资源，因此必须限制 Serenity 并发、超时和内存，不能把“分进程”误认为“没有资源隔离需求”。
- 旧前瞻评估数据仍保留用于研究，但不再控制 3% 权重晋升。

## Migration

新增现行目标与批次存储，不覆盖旧 Serenity 证据。部署最新共享镜像并重建 `gp` 与 `gp-worker`。确认统一 worker 正常后，按确切名称移除旧停止的 `gp-gp-serenity-worker-1` 容器；不使用 Compose orphan 批量删除。

## Rollback

任何 Serenity 异常自动回到稳定 0% 哨兵，无需切换基础推荐路径。若代码回滚，保留新增追加记录并让旧版本忽略它们；不得恢复请求内抓取、退役合同或静态候选回退。
