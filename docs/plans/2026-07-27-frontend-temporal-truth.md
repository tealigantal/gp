# 前端时间事实与恢复状态呈现

## Purpose / Big Picture

将后端已经确定的回答时刻、市场阶段、计划交易日和日K恢复状态直接、清晰地呈现在聊天工作区。用户无需从聊天正文反推“当前能否执行”或把已结束计划误读为下一交易日计划。

## Context and Orientation

- 当前前端只读 `GET /api/health` 与 `GET /api/recommendation/current`，并已经声明了 `market_recovery` 类型。
- 现有侧栏仅以小字显示恢复计数；主决策区域只展示计划交易日和日线日期，无法表达“当前时刻相对于该计划”的关系。
- 后端 `ConversationService` 已将回答时刻投影与历史 `RuntimeObservation` 分开；前端必须消费相同的只读健康事实，不能重新计算候选、排序或修改计划/会话。

## Validation and Acceptance

验收要求：收盘后页面明确提示当前发布计划已结束、仅供回顾，同时明确下一交易日的目标日、所需日K和生成状态；不得把旧计划过期表述为“没有明日计划”。恢复中显示目标日和覆盖/失败情况；正常交易时不产生错误的收盘提示；聊天历史、当前候选和只读 API 行为不变。

## Idempotence and Recovery

本次仅修改前端渲染和现有测试。重新加载页面可重新取得同一健康状态；回退可直接还原前端源码，不需要回写计划、发布、会话或任何数据库。

## Surprises & Discoveries

- 真实 2026-07-27 22:46 健康响应仍把绑定 RuntimeObservation 的 `closing_auction` 和 `tradeable` 放在既有顶层字段；这些是发布历史事实，不是服务端当前时刻。直接让前端沿用它们会重现聊天已修复的时间错述。
- 因此没有用浏览器本地时钟“打补丁”，而是在服务端复用聊天的当前时间投影，新增兼容性字段 `market_now`，并让网页在该字段缺失时失败关闭。

## Decision Log

- 只使用后端健康字段和已发布计划的不可变事实；前端不请求采集、不触发日K恢复，也不复用历史运行观察作为“当前时间”。
- 当前发布计划与下一交易日目标是两个不同投影：前者可以过期，后者仍可处于等待日K、待发布或已发布状态。
- 保留既有顶层历史运行字段，避免不必要的 API 破坏；新增 `market_now` 作为唯一的“现在”语义，完成消费者切换后再由后续显式契约变更决定是否清理旧字段。

## Interfaces and Dependencies

`GET /api/health` 非破坏性增加 `market_now` 与 `next_plan_target`：前者是服务端上海时钟的当前发布计划关系和执行许可，后者是服务端同一时刻解析出的下一计划交易日、所需日K、覆盖/重试和发布状态。前端只消费这两个投影，不将历史运行字段重新解释为当前状态，也不自行计算下一交易日。

## Outcomes & Retrospective

已完成。`ConversationService` 和 `/api/health` 共用 `project_current_market` 与 `project_next_plan_target`，避免聊天和网页分别解释当前时刻或从旧计划推断下一计划。旧 `market_phase` / `tradeability_state` 仍是绑定发布的历史 RuntimeObservation 摘要，未被删除或重命名；网页将“当前发布计划已结束，仅供回顾”与“下一交易日计划生成中/已发布”并列展示。收盘后日K未齐时，页面明确说明目标交易日、所需日K和覆盖进度；日K齐全且发布成功后，页面改为“下一交易日计划已发布，等待开盘”。
