# Architecture

The decision pipeline normalizes provider data at explicit adapters, applies Signal, Market Memory, Probability, Risk, Adaptive, and Serenity evidence, and emits a typed plan commit command. `PlanService`, `RuntimeService`, and `PublicationService` own the only application write path. The storage boundary verifies schema identity before any normal operation.

The browser is a read-and-converse projection served by Nginx. It consumes only current publication, health, canonical conversation list/detail, and chat routes. Browser state may optimistically display the user's pending turn, but the ordered persisted `ConversationTurn` records replace it after the response. Candidate filtering is limited to displaying `disposition=selected` entries in their existing engine order; no selection, ranking, scoring, or execution decision exists in frontend code.

The browser atomically accepts health and current-publication reads only when their publication IDs match, with one bounded retry for pointer rollover. Chat responses never overwrite the current-publication state. Their bound publication supplies an in-memory, trusted publication-to-plan lineage hint for the active session; browser storage is not a source of truth. Unknown or different-plan sessions remain isolated from the current candidate panel.

Conversation deletion is a narrow lifecycle operation. The store deletes one `sessions` row by primary key; foreign keys cascade only to that session's `turns` and `claims`. A `deleted_sessions` tombstone prevents delayed or retried chat requests from recreating the same session ID. The browser invalidates stale list reads after deletion and filters tombstoned IDs from concurrent responses, while the current publication state remains independent.

Compose contains the core `gp`, `gp-worker`, and `web` services. API and web health checks make startup readiness observable, and worker/web startup waits for API health. Nginx proxies `/api/` to `gp:8000` and serves the single-page application for all other paths.

`gp-worker` supervises three independent failure domains. `MarketDayOrchestrator` owns the durable daily run ledger in `store/market_runs.db`, freezes the denominator, verifies exact target-date coverage and invokes the plan/runtime/lunch publication handoffs. A short-lived child performs bounded daily-bar batches so source I/O cannot block the parent heartbeat. A separate child process owns Serenity network collection, PDF parsing, source verification, lease, and retry. The plan path first freezes the base Top-30 and publishes its content-addressed target, then reads only an already committed exact Serenity batch. It never waits for collection. A complete batch contributes `0.03 × alpha` where alpha is bounded to `[-1,1]`; any partial, failed, stale, or mismatched batch maps to one stable zero lane for every finalist. Equivalent failures therefore cannot churn plan identity, while a new complete content digest can produce a new immutable plan.

Daily readiness binds an exact required trading date to one frozen raw main-board universe. Only a fresh, same-session, field-complete zero-trading row can prove that a symbol should have no bar; all other missing evidence remains fail closed. The market-run ledger records symbol progress and leases, rereads `history.db` by exact date after every 100-symbol batch, and retries only missing symbols. It freezes at 14:57, probes at 15:05, and may start current-day full-market fetching only at 15:20. Startup recovery runs missing dates old-to-new; an unavailable historical denominator is explicitly `reconstructed_current_universe` and never creates a historical recommendation. `RealRecommendationProducer` is read-only and accepts only a complete frozen run. Both publication layers reject incomplete, pending, fallback or unavailable plans, so recovery retains the last complete current pointer.

Serenity keeps `pypdf` as the text-layer fast path. A structurally valid zero-text PDF alone may enter the bounded PDFium/Tesseract child-process lane; identity, topic, confidence and a higher-resolution directional/percentage check must all agree. Parse method and OCR audit data remain in append-only document/batch JSON, and the v2 semantic revision prevents reuse of v1 batches without changing SQL or public contracts.

At lunch, the same core worker has one additional ordered lane. From 11:32 it reads the current same-session base plan and starts a bounded child process to fetch the frozen Top-30 plus CSI300 outside database transactions. The parent terminates collection on total-budget expiry. After validating an exact 09:35–11:30 batch and computing the deterministic lunch score, it takes a cross-process write lock, rechecks the original base publication, appends a new plan and its 11:30 runtime, and only then uses a compare-and-swap publication commit to move the current pointer. Failure before the last step leaves the morning publication visible. During lunch the normal runtime producer returns the existing observation, so manual or scheduled refresh cannot replace the result with an empty unavailable observation. During the afternoon, periodic daily production cannot replace the same-session lunch plan.

The contract database remains `contract_kernel.v1`. Plan, runtime and publication rows are append-only. Store writes reject conflicting content identities, mismatched runtime lineage, concurrent stale pointer expectations, backward session/slot publications, and plans that lack complete target-day evidence. No network request runs while a contract transaction is held. T+5 maturity remains outside the realtime recommendation lane and is never read as a future result.
